# 通知跳转与飞书离线推送验收记录

通知点击已完成 Bilibili、钉钉、淘宝的本地重放验收。飞书离线推送尚未验收通过，不能将连接正常或注册成功视为离线推送已修复。

## 通知点击

Bilibili 原始通知的本地重放可复现：点击后打开首页，Android 同时拒绝启动其 MiPush `PushMessageHandler` 后台服务。安装版 XMSF 的转发路径未保留 SDK 使用的 `mipush_notified` 标记。

修复范围限定为 SystemUI 点击、由 XMSF 创建的 PendingIntent，以及 30 秒内匹配原始载荷摘要的投递。保留原始载荷，补回点击标记，并申请短期系统及栖序放行；不放开全局后台启动。补回标记后的第一轮仍被系统拒绝。进一步反射检查确认：本 ROM 的实际公共调用路径进入 14 参数 `startServiceLocked`，原 10 参数钩子漏掉该路径。改为实际入口后，23:14 的本地重放记录到服务启动成功，页面进入原通知对应的“荣耀 WIN2”视频详情，完成 Bilibili 单例验收。

本地重放仅验证点击路径，不证明云端投递正常。服务启动成功也不等于已打开正确内容页。

## 可选后台连接保活

飞书应用详情新增默认关闭的“后台连接保活”，GUI 与 root CLI 共用同一状态。每 30 秒检查主进程，退出时启动飞书原生后台服务，半小时最多尝试 3 次；尊重强行停止和禁用，用户尚未解锁时不启动。依赖栖序，启用前保存原方案及逐应用覆盖值；关闭只还原仍等于本功能设置的字段，保留用户后续修改。方案或相关规则发生变化时不再自动拉起。

这不是 MiPush／FCM 离线推送修复。第 010、012 条在自动恢复后的稳定后台状态收到；第 010 条点击进入对应会话。第 011 条在连接尚未建立时发送，没有形成通知，说明恢复窗口仍可能漏通知。

第 009 条发布后约 5 秒被飞书主动取消。系统事件记录确认调用者是飞书进程，反编译定位到启动配置任务中的通知清理。首次在 NotificationManager.cancelAll 层的保护未命中该异步路径，第 013 条仍被取消。最终改在该启动任务调用的原生 clearNotification 入口保护，限定于该任务、启用保活且应用处于后台；用户进入前台后的清理不受影响。第 014 条在启动窗口发布，随后记录到保护事件，等待后通知仍然存在；未出现新的崩溃。

CLI 示例（revision 使用 `keepalive.get` 实际返回值）：

```sh
qixin rpc '{"command":"keepalive.get"}'
qixin rpc '{"command":"keepalive.set","enabled":true,"expectedRevision":0}'
qixin rpc '{"command":"keepalive.set","enabled":false,"expectedRevision":1}'
```

启用后 `restorePending=true` 表示保留了待关闭时恢复的策略快照。关闭后若恢复失败，可再次关闭重试，恢复完成前不会继续拉起。`running` 仅表示进程存在，不表示连接或消息验收成功。

第 015 条在锁屏状态下收到，验证的是原生连接已建立后的收信，不是强杀后的云端唤醒。测试结束已关闭保活，`restorePending=false`，原栖序逐应用覆盖值与测试前逐字段相等。USB 亮屏调试会话已结束，未修改锁屏凭据。
