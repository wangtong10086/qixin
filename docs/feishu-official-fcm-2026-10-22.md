# 飞书官网版与 FCM 验证

最新结果：官网飞书 8.3.6 开启原生 FCM，配合栖信 alpha5，在关闭保活、所有飞书进程退出且 `stopped=false` 的条件下，桌面与锁屏两轮真实 FCM 投递及通知留存均通过。通知持续保留超过两分钟，点击进入正确会话，手动划除后不重发。以下按阶段保留调查与修复证据；早期“未通过”是当时结果。

- 官网与原小米应用商店 APK 的签名证书一致；ZIP 内代码、资源条目的 CRC 与长度全部一致。
- 原渠道标识为 `xiaomi_1161_x64`，官网渠道为 `feishu_website_organic_and`，均为构建 `748a820`。
- 证书 SHA-256：`d3f0e06b185518663e2afea2fcd528f5b0b8ca6c3b47e57b22893715043572ec`。
- 原 APK SHA-256：`6eb51bb1610a5e86b8e79c1f742ac9abeb3e6104a638ec2e98c662cfc035b2ae`。
- 官网 APK SHA-256：`f9e4f3409599650e77c9975df08ea9a524445d3caf82c5bca4a3763db68727e5`。

完整备份原 APK、CE/DE 数据后，以相同签名覆盖安装，未清除登录、聊天或 token 数据。官网包不等于独立的“FCM 专用版”，不能仅凭更换渠道推断推送已经切换。

## 原生开关是关键

通过飞书头像 → 设置 → 通知，找到“开启谷歌 FCM 推送服务”，现场原状态为关闭。开启后正常重启应用，观察到：

| 项目 | 之前 | 之后 |
|---|---|---|
| 本地支持通道 | `[1,8,23,26]` | `[1,5,8,23,26]` |
| 业务允许通道 | `[23]` | `[5,23]` |
| FCM 业务支持 | not-supported | supported |
| FCM token 上报 | 无本轮成功证据 | server-accepted |

通道 5 是 FCM，通道 23 是既有 Umeng mini 通道。未伪造服务端允许列表或注册 token，未修改 APK，也没有新增 hook。由包内实现可见，国内版 FCM 可用性还检查本机 Google Play/Play Services 和原生 FCM 用户开关；设置入口还受企业认证状态影响。因此只看到 FCM SDK 组件或旧 token 缓存不足以判定可用。

本次先替换渠道，再开启开关，未做原渠道开启开关的对照，所以不能证明“必须官网下载”。代码资源相同且开关直接参与可用性判断，表明原生开关是本次关键变化。

## 离线测试边界

关闭保活，退出飞书全部进程，保持 `stopped=false`。测试期间仅临时拦截飞书的 MiPush 投递，其他应用小米推送不变。以 GMS 来源的 FCM dispatch 和后续 notification 事件验收；进程存在、普通长连接收信或消息补收均不计为 FCM 离线成功。

直接用 ADB 启动内部通知设置页缺少飞书会话参数，会触发崩溃；已改为应用内导航，不应把这一测试入口问题归因于官网包兼容性。

当前手机账号与早期 CLI 的同组织测试账号不同，不能向旧收件人发送消息后作为当前手机的验证。待当前账号收到真实测试消息后补记投递结果。

第一轮退出后观察窗口未出现新 FCM 投递或通知，飞书进程仍为空；这不等于已发送消息丢失，因为尚未收到当前账号测试消息的发送确认。窗口结束后已逐字段恢复小米运行时原配置，保留官网包和原生 FCM 开关开启状态。后续即使保留小米配置，也可通过 GMS 来源的系统派发事件明确识别 FCM。

## 真实 FCM 离线投递验收补充

2026-10-22，手机切回既有同组织 `wangtong` 测试账号。使用已授权的独立测试账号，以 user 身份通过飞书 CLI 发送两条编号消息；未使用开发 CLI 配置。

每次测试均先退出飞书所有进程，保持 `stopped=false`，保活关闭，等待约 45 秒确认没有自行重启。测试期间仅拦截飞书 MiPush。记录如下（北京时间）：

| 测试 | 发送 | FCM 系统派发 | 通知发布 | 飞书主动撤销 |
|---|---|---|---|---|
| FCM-018 | 14:12:49 | 14:12:49.491 | 14:12:58.661 | 14:13:03.468 |
| FCM-019 | 14:16:53 | 14:16:53.444 | 14:16:55.918 | 14:16:57.053 |

两轮均记录 `com.google.android.c2dm.intent.RECEIVE`、FCM high 优先级系统派发和后续通知发布；第二轮还在系统通知快照中匹配到 `FCM-019` 内容。可以确认 **FCM 能在飞书进程完全退出后唤醒应用并展示对应通知**。

但通知留存失败：系统事件记录显示调用方为飞书自身 UID，`notification_cancel_all` 后以 reason 9 撤销刚发布的通知。两轮分别留存约 4.8 秒、1.1 秒。当前已有的启动通知清理保护仅在 `nativeKeepalive=true` 时生效，本次为验证离线 FCM 关闭保活，因而没有触发该保护。具体清理调用点与既有启动任务问题一致仍需进一步钩子证据确认；本次已确认的是应用自身 cancelAll，而非 FCM 未投递。

结论：注册与 FCM 离线投递通过，通知持续可见尚未通过。测试后已逐字段恢复原 MiPush 配置，保活仍关闭，保留官网版及原生 FCM 开关；停止了临时连续采样。本轮仅验收和定位，没有修改清理保护代码。

## alpha5 启动清理修复

飞书 8.3.6 的 `UpdateOfflinePushConfigTask$a.run` 在更新推送配置后调用 `NotificationApiImpl.clearNotification()`，后者通过 `NotificationClearUtils` 将清理提交到线程池。必须在提交前识别启动任务；在最终 `cancelAll` 线程上读取原线程的标记无法识别这条路径。

FCM-020 只修复上述入口后，通知仍在约一秒后被撤销。FCM-021 的只读调用栈确认另一入口：`StatusMachineController$d.run → NotificationDependency.a → NotificationApiImpl.clearNotification`。消息列表控制器完成初始化后，会延迟一秒执行该任务；后台唤醒也会触发。账号切换监听器通过 `NotificationClearUtils` 直接清理，属于不同路径。

栖信复用既有任务标记及通知 API 钩子，同时覆盖上述两个已验证的初始化任务，移除 `nativeKeepalive` 前提。管理模式下，只有这两个任务内部、进程重要性低于可见级别的调用被阻止；前台或可见、观察模式、配置尚未就绪及其他调用路径均执行飞书原方法。推送配置更新仍执行，没有全局禁用取消通知，也没有重新发布或复制通知。

`startup-notification-cleanup` 事件包含具体入口、模式和进程重要性，结果为 `preserved-background-notifications` 或 `allowed-notification-cleanup`。首轮配置获取立即在既有工作线程进行；钩子不等待 IPC，不读取通知正文。CLI 与配置格式不变。

核心回归覆盖关闭／开启保活、前台／后台、启动／其他清理及配置未就绪，28 项核心测试通过；release 构建与 lint 通过。最终安装包版本为 0.1.0-alpha5 / 5。
